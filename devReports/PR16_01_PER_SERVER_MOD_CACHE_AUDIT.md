# PR16-01 — persistent per-server mod-cache audit

Date: 2026-10-11  
Scope: read-only investigation of the active DZLL checkout and one existing local SQLite snapshot. No DZLL/Steam launch, network request, dependency installation, source/test/instrumentation/tracker/Forge/MEMORY.md edit, review-clone inspection, or Git mutation occurred. The only created file is this report. Existing dirty and untracked work was preserved.

## Evidence classes and decision

**Measured here:** the local database sample and isolated Python timing proxies below. **Maintainer-provided runtime benchmark:** 11,980 servers; original GTK DB callback 4,140 ms; current callback 2,907 ms; current main-loop stall approximately 3 seconds; per-server preview/search phase 1,322 ms; persistent global suggestion-cache phase approximately 360 ms. These runtime figures concern a different 11,980-row input than the 11,874-row local snapshot. **Source-confirmed:** control flow and data contracts cited below. **Unverified hypothesis:** a warm per-server cache could reduce the 1,322 ms phase, but cache I/O, restoration, hashing and validation consume part of that budget; no startup gain or historical hit rate was measured here.

Recommendation: prototype a **versioned, bounded, atomic JSON snapshot keyed by canonical endpoint plus exact raw-mod digest**, with per-row fallback and an explicit benchmark gate. Store only preview count/string and the per-server search sets. Keep the DB `modCount` override outside the cache. Exclude the global suggestion catalogue, row objects, and authoritative join data. A single whole-file load is the simplest first experiment at this scale, provided it is measured on the actual GTK path. If load/restore cost or memory erases the gain, do not ship persistence; then consider pure-Python preparation off GTK separately. The existing load-local parse reuse and v2 global suggestion cache must stay intact.

## Current data flow and consumers

1. `read_servers_from_db()` selects `mods` and `modCount`, ordered by players then ping, and returns dictionaries (`src/dzll_launcher/db.py:123-151`). Normal startup fetch/read is in a DB worker, with a 30-second watchdog that can read locally on GTK and provisionally apply rows (`src/dzll_launcher/window.py:5430-5466,5523-5578`). A successful final callback can replace that provisional list; failed fetch paths retain or read the local DB (`window.py:5468-5521`). Manual refresh fetches, reads, and applies through the same `_apply_db_rows()` (`window.py:5580-5633`).
2. `_apply_db_rows()` validates endpoints before `_load_rows_into_store()` (`window.py:5749-5782`). The loader clears the source store and endpoint map, validates again, and accepts `mods` only when it is a string (`window.py:5818-5847,5866-5868`). `normalize_server_endpoint()` requires strict IPv4 and integer game/query ports, with a fallback query port only for missing `qport` (`src/dzll_launcher/server_endpoint.py:10-61`). `fav_key(ip,gport)` is the canonical game-server identity; `qport` is not part of it (`window.py:495-496,5902,5950-5951`).
3. `ParsedServerMods.from_json()` decodes a nonempty raw string once per accepted row, using an empty list for malformed or non-list JSON; its cleaned-name memo is scoped to that parsed instance and distinguishes the Workshop-ID argument (`src/dzll_launcher/mod_parsed.py:9-32`). `parse_mods_preview()` walks dictionary items in original order, keeps duplicate cleaned names, counts usable names, and displays the first eight plus `", ..."` when truncated (`window.py:516-553,5870-5871`). A convertible DB `modCount` overrides only the displayed count after preview computation (`window.py:5874-5878`). The preview and count enter `ServerObject`; raw JSON remains attached (`window.py:5908-5921`; `src/dzll_launcher/ui_row.py:452-454`).
4. `build_server_mod_index()` uses the same parsed items and memo. It collects digit-only stringified Workshop IDs and cleaned normalized names, compact names, and split tokens into frozensets; `names` aliases the same compact-name frozenset as `compact_names` (`src/dzll_launcher/mod_search.py:17-24,37-39,100-149`). The loader attaches the index to each new object, appends the object to the source store, and overwrites `_obj_by_key[k]` and the parsed sidecar for duplicate canonical endpoints (`window.py:5934-5952`). Duplicate objects may remain in the source store even though the endpoint map retains the last one; a cache must preserve this current behavior and must not let the first row's data satisfy the second row.
5. The temporary parsed sidecar is used only while `_rebuild_mod_suggestion_index()` builds a missing global catalogue from the **final** endpoint map, then is discarded (`window.py:5968-5975,8489-8501`). A valid global persistent cache can bypass that build and remains ready across subsequent DB loads (`window.py:8453-8487`). The global builder uses ID-first/name-fallback identities, per-server deduplication, name frequencies, canonical/display-name selection, sorting and prefix/exact lookup maps (`src/dzll_launcher/mod_suggestions.py:53-68,110-149,232-295`). Its v2 disk cache is a separate 64 MiB, byte-digest-checked, atomically written XDG cache with its own lifecycle (`src/dzll_launcher/mod_suggestion_cache.py:21-34,125-280`; `window.py:8517-8591`). The prior optimisation reports document these established changes.

The UI reads it for exact chips and autocomplete (`window.py:8264-8305,8903-8915`; `src/dzll_launcher/mod_suggestions.py:232-295`). The consumers have deliberately different ID/name edge rules: preview and popover use `steamWorkshopId or ""`, search stringifies non-`None` IDs (including `0`), suggestions use their own cleaner and skip empty names, while join accepts positive integer IDs (`window.py:536-540`; `mod_search.py:124-139`; `mod_suggestions.py:53-64,243-273`; `workshop_mods.py:37-53`). A cache must reproduce the existing derived outputs, not impose a new common parser rule. The ordinary load performs one decode per accepted row today; persistence may skip that decode on a hit while leaving raw JSON on the object.

## Local database sample — measured, not historical

I opened `/home/gbrown/.local/share/dzll/dzll-servers.db` with `mode=ro&immutable=1`; no DB files were written. The file was 23,465,984 bytes and its table had 11,874 rows. The sample followed the reader's `ORDER BY players DESC, ping ASC` and the source endpoint/string rules. All 11,874 rows had accepted endpoints and valid JSON lists; 10,168 lists were nonempty and contained dictionary items, and 1,706 were empty lists. There were no duplicate canonical endpoints in this snapshot. These counts describe **this snapshot only** and cannot yield a database-update or cross-launch change rate.

There were 9,219 distinct exact raw payload strings: 9,218 nonempty-list payloads plus one `[]` payload shared by 1,706 servers. Counting all rows, 2,655 are repeats beyond the first occurrence of a payload; excluding the empty-list group, only **950 of 10,168 nonempty-mod rows** repeat an earlier exact payload (9.34%). Across all payloads, 2,953 rows belong to a group of size at least two. There are 8,921 singleton payload groups. Thus content-addressing saves little nonempty derived-data duplication in this sample; the conspicuous duplicate group is the trivial empty list. A perfect same-snapshot content memo could avoid at most those 950 nonempty rebuilds plus trivial empty-list work, without proving persistent warm hits.

Raw payload strings total 17,177,531 UTF-8 bytes across rows, or 16,593,211 bytes once per distinct payload. A compact JSON estimate containing the current preview count/string and four unique search sets for every endpoint totaled **21,849,451 bytes** before endpoint keys, digests, envelope and storage overhead. Storing one such record per exact unique payload totaled **20,879,631 bytes**; the maximum derived-body saving from sharing is approximately 970 kB (4.4%) on this snapshot. Preview strings alone total 1,399,620 bytes; index-only JSON bodies total 19,955,143 bytes. A compact endpoint/digest/index-only array was 21,040,672 bytes in a one-off proxy. These are serialized-body estimates, not actual cache-file, SQLite, in-memory, compression, or peak-RSS measurements. Storing raw strings as identity adds up to 17.2 MB of raw payload content before JSON escaping and metadata; digest identity avoids that copy at the cost of hashing and collision checks. If `[]` is represented by an empty sentinel rather than a disk entry, the useful entry count is 10,168 per endpoint or 9,218 by nonempty content.

One-off, in-process, hot-page-cache proxies on this snapshot (three sequential repetitions; no DZLL/GTK): building only the per-server search index from raw JSON took **1,020/1,128/1,258 ms**; hashing every raw payload with SHA-256 took **10/10/10 ms**; `json.loads()` plus shallow shape/type checks and frozenset restoration of the 21.0 MB index-only proxy took **159/186/198 ms**. This suggests restoration *can* be cheaper than rebuilding the search index, but excludes actual disk read, full bounds and integrity checks, preview restoration, endpoint matching, DB callback contention and peak memory. It cannot be subtracted directly from the supplied 1,322 ms GTK preview/search phase. The existing approximately 360 ms global-cache cost remains separate.

## Identity, invalidation, and Forge fingerprint

Use a namespaced cache schema/normalization version plus canonical `ip:gport`, then a digest of the **exact UTF-8 bytes of the accepted raw `mods` string**. Recompute the digest from the current DB row before accepting a hit. Exact bytes avoid accidentally treating reordered arrays, duplicate entries, changed display names, whitespace changes, or ID-type changes as equivalent; some of those changes affect preview order or search behavior. A digest should be SHA-256 or equivalent stable content hash, with the cache file's own integrity check and strict length/type bounds. For collision paranoia, exact raw text comparison is stronger but carries roughly 17 MB additional payload content in this sample; a digest is an engineering tradeoff, not a mathematical proof of equality. Do not use Python's process-randomized `hash()`, `modCount`, DB mtime, name, ping, query port, or a whole-DB checksum as the sole mod identity. Version changes must cover preview rules, name cleaning, search normalization/tokenization, aliases if serialized results ever depend on them, and record schema. Query alias logic currently runs at match time, but bump conservatively when semantics change.

The local `servers` table has `mods` and `modCount` but no mod-fingerprint column (read-only `PRAGMA table_info`). A Forge-provided digest could avoid DZLL's local hashing only if Forge published a stable, documented digest of the exact bytes DZLL consumes and kept it synchronized through every publication transformation. The measured local hashing proxy is about 10 ms for all rows versus a 1,322 ms phase, so this is not a meaningful current bottleneck. A server-side semantic fingerprint would be harder to trust for preview order, duplicates and normalization versions. It would add cross-repository schema/version coordination and would still require a safe local fallback for older DBs. No Forge change is recommended; no Forge source was modified or needed for this conclusion.

## Cache design comparison

| Design | Benefit and fit | Cost / failure concern |
|---|---|---|
| Per-endpoint persisted derived record | Directly answers unchanged-server reuse; current input is already keyed by canonical `ip:gport`; easy per-row digest check and replacement. Preferred first prototype. | Up to about 10,168 useful entries here, roughly 22 MB compact derived body plus keys/digests/envelope. Requires pruning and duplicate-row policy. |
| Content-addressed records shared by endpoints | Saves rebuild for identical payloads across endpoints; can keep a separate endpoint-to-digest map. | Only 950 nonempty repeated-row opportunities and about 970 kB maximum derived-body saving here. Added reference counting/generation complexity is not justified by this snapshot. |
| Bounded versioned JSON snapshot | One file, deterministic validation, straightforward atomic replace, no new runtime dependency; follows the existing global-cache pattern without changing it. | Whole-file decode/restore and rewrite cost; a corrupted file is a whole-file miss. Must bound file/entries/field lengths and use a fresh namespace/version. |
| SQLite sidecar | Indexed endpoint lookup, transactions, selective updates and deletion can help if the cache grows far beyond this scale or only a small subset is needed. | Extra DB/file lifecycle, many lookup calls unless batched, schema migration/locking/WAL complexity, potential profile writes and startup I/O. The browser currently constructs all rows and their indexes, so selective startup reads offer little inherent advantage. |
| Whole-cache load | One bounded read and parse may be cheaper than 10k+ point lookups; simplest benchmark target. | The full ~20+ MB must be decoded/validated on a main-thread callback unless later moved; cold/corrupt loads pay both cache check and rebuild. |
| Selective/lazy load | Could reduce memory and work for a genuinely small needed subset. | Current filtering can examine every object at any time, including after a query change; lazy misses may move the stall to typing/filtering and demand another concurrency policy. Batch lookup is preferable to per-row SQLite calls if evaluated later. |

## Required lifecycle and failure behavior

- **Changed mods:** current-row digest mismatch forces a rebuild from that row's raw string and replaces the prior endpoint record only after the new derived result is valid. Missing endpoint records also rebuild. A changed `modCount` alone must still update displayed count from the current DB, without invalidating preview/search derived solely from raw `mods`.
- **Empty/invalid input:** preserve `""` for non-string DB values and the existing empty results for malformed/non-list JSON. An empty-list/invalid sentinel may avoid disk storage, but validity must be recomputed from current input as needed and must not turn a bad payload into stale prior results. Bound raw length and cache metadata before parsing/restoration; oversized input falls back to ordinary current behavior, not stale data.
- **Duplicate endpoints:** process every accepted row in DB order with that row's raw digest. The last row wins in `_obj_by_key`; the current source store may still contain both objects. A snapshot cache should publish one record for the final endpoint value while each row gets its own correct derived output during the load. No first-row leak.
- **Disappear/reappear and pruning:** a missing server must not appear in the current model because a cache record exists. Keep only records for final endpoints of a successful final DB load; a later reappearance with matching digest may hit only if retained by an explicit bounded retention policy. Simplest is prune on final successful publication, accepting a miss after reappearance. Add hard file/entry/field-size caps and avoid indefinite tombstones.
- **Provisional/final and failed fetch:** a provisional local load can read hits and rebuild misses, but must not publish a pruned disk snapshot. Publish only the successfully applied final generation; failed fetch keeps the current usable data and should not wipe the cache. Guard any deferred publication with generation/shutdown checks, like the existing suggestion-refresh path (`window.py:5818-5820,8540-8572`). A synchronous first prototype should still recheck the generation before writing.
- **Manual refresh:** successful application uses the same per-row identity check and final publication. A failed manual fetch does not apply rows and must not alter the cache (`window.py:5602-5633`).
- **Corrupt/incompatible cache or failed write:** size/integrity/schema/type failure becomes a miss; rebuild from current DB. Write to a same-directory temporary file and atomically replace after complete serialization/validation; failure leaves the previous file and in-memory current results usable. Never deserialize executable formats or accept unbounded nested data. Separate this cache's path and version from `mod_suggestions_v1.json` despite that file's v2 content (`src/dzll_launcher/mod_suggestion_cache.py:21-34,246-280`).
- **Search/suggestion consistency:** a cached search index must exactly match the current raw row. Do not derive global suggestion counts from all raw DB rows or endpoint cache records because overwritten duplicates would be counted; continue to use final `_obj_by_key` semantics. Do not make the global cache depend on per-server cache freshness. Confirm selected chips, filters and autocomplete after reload; note the existing global catalogue's monthly refresh policy may independently delay a change in suggestions.
- **Join authority:** raw `mods_json` remains on `ServerObject`, and join/preparation calls `parse_mods_from_db()` on demand. No persisted derived index may supply required IDs or excuse the separate join-time freshness policy.

## Implementation and verification plan for a later task

1. First add aggregate, opt-in measurements around cache stat/read, integrity, JSON decode, record restoration/validation, digest matching, hit/miss rebuild, serialization/write and peak RSS, with no per-server logs. Record retained endpoint count, hits, misses, malformed/oversized records and bytes. Keep the current `mod_preview_index` and GTK callback phase definitions comparable.
2. Prototype a fresh bounded JSON format and exact-output restoration helper, preserving the current `ParsedServerMods` fallback on each miss and raw JSON on each object. Construct no GObject or GTK model off thread. Avoid writing on provisional loads; atomically publish a final-generation endpoint snapshot only when contents changed. Cap the file based on a measured full snapshot with headroom (for example 64 MiB initially), plus explicit count/string/list bounds. Treat over-limit as a safe no-cache result, not a startup failure.
3. Differentially test the cache hit and fallback against current builders on detached fixtures and adversarial rows: empty/malformed/non-list/non-string JSON, mixed item types, duplicate names/IDs, zero and odd ID types, Unicode/control text, >8 names, DB count override, duplicate canonical endpoints with different mods, query-port changes, disappeared/reappeared endpoints, stale schema, truncated/tampered/oversized cache, and write failure. Compare preview/count, all five index fields and `server_matches_mod_query()` across numeric IDs, aliases, exact/compact names and token prefixes. Verify Companion snapshot, raw popover and on-demand join parse remain independent. Test provisional then final, manual success/failure, generation/shutdown, and suggestions/chips through reload. Existing `tests/test_browser_server_ingestion_validation.py`, `tests/test_mod_name_normalization.py`, and `tests/test_mod_suggestion_cache.py` are relevant starting points; use isolated HOME/XDG and detached DB fixtures, never the real profile for tests.
4. Benchmark at least three matched cold-cache and warm-cache launches on the same 11,980-row DB/settings/hardware, plus a changed-small-subset DB update and a corrupt-cache fallback. Report median and range for hit rate, cache stages, preview/search phase, global-cache phase, GTK DB callback, maximum main-loop stall, time to usable list and peak RSS. The warm hit rate must be **measured across actual snapshots/launches**, not inferred from today's duplicate count. A useful acceptance gate is exact output equivalence and a reproducible reduction in both the 1,322 ms preview/search phase and approximately 3-second GTK stall that exceeds run-to-run variance, with acceptable RSS/disk overhead and no cold/corrupt regression beyond a documented small cache-check cost. Reject the cache if total callback time merely moves into deserialization or writing.

Pure-Python decode/cleaning/index construction could later move to a worker with plain immutable results and generation/failure recovery, while GObject creation and model mutations stay on GTK. That may shorten the uninterrupted main-loop stall even if total CPU time remains similar under the GIL. It is a separate concurrency change and is **not implemented** here.
