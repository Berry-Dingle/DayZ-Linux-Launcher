# PR16-01 — mod-indexing bottleneck audit

Date: 2026-10-10  
Repository: official DayZ-Linux-Launcher, active `src/dzll_launcher` tree. Scope: read-only source, prior audit/instrumentation report, tracker, and supplied one-run timings. No DZLL launch, network request, test run, source/test/instrumentation/tracker edit, dependency install, or Git mutation was performed.

## Evidence and interpretation

The supplied first baseline has 11,980 rows, `mod_preview_index` 1,619 ms and `global_mod_suggestion_index` 1,503 ms. These are consecutive GTK callback phases, totaling **3,122 ms**, about **75%** of the supplied 4,153 ms DB GTK callback. The 4,264 ms main-loop stall is consistent with that long callback, but does not attribute every millisecond to indexing. The 13,213 ms activation-to-overlay-dismissal time includes earlier DB/update/network and later warmup work. These are one-run observations, not a repeatable benchmark. The phase definitions are in `src/dzll_launcher/window.py:5834-5840`, `5906-5909`, `5920-5943`, and `devReports/PR16_01_STARTUP_INSTRUMENTATION_REPORT.md:17-34`. The 1,619 ms bucket combines preview and per-server search-index work; the 1,503 ms bucket combines global JSON decode, aggregation, final entry construction, sorting and lookup maps. Existing measurements cannot apportion either bucket further.

## Current execution flow

1. `read_servers_from_db()` selects `mods` and `modCount` alongside server fields, fetches SQLite rows and converts them to dictionaries in the DB worker (`src/dzll_launcher/db.py:123-151`, `src/dzll_launcher/window.py:5510-5540`). The normal data read is off GTK; the DB completion callback applies rows on GTK (`src/dzll_launcher/window.py:5420-5445`, `5723-5752`).
2. GTK endpoint validation makes an accepted-row list, and `_load_rows_into_store()` normalizes endpoints again and clears/rebuilds the source object model (`src/dzll_launcher/window.py:5723-5752`, `5788-5815`). For each valid row, it accepts `mods` only if it is a string, otherwise uses `""` (`src/dzll_launcher/window.py:5834-5835`).
3. `parse_mods_preview()` JSON-decodes that string, walks dictionary items, cleans usable mod names, counts them and joins at most eight names with an ellipsis (`src/dzll_launcher/window.py:507-543`). The DB's `modCount`, if convertible, overrides only the displayed count; it does not replace preview parsing (`src/dzll_launcher/window.py:5836-5845`). This produces `ServerObject.mod_count` and `mods_preview` (`src/dzll_launcher/window.py:5880-5888`; `src/dzll_launcher/ui_row.py:452-454`).
4. The same raw string is decoded again by `build_server_mod_index()`. It collects numeric Workshop IDs, normalized names, compact names and tokens into per-server frozensets; it cleans names again (`src/dzll_launcher/mod_search.py:99-146`). The result is attached to each GObject as `mod_search_index` (`src/dzll_launcher/window.py:5906-5909`). `ServerObject` construction/property writes and source `Gio.ListStore.append` are separate GTK/GObject phases (`src/dzll_launcher/window.py:5873-5899`, `5912-5918`; `src/dzll_launcher/ui_row.py:437-487`).
5. Once all rows are appended, `_rebuild_mod_suggestion_index()` scans `_obj_by_key.values()`, allocates a list of every retained object's `mods_json`, and passes it to `build_mod_suggestion_index()` (`src/dzll_launcher/window.py:5934-5938`, `8409-8417`). That builder decodes each JSON string for a **third** time and allocates a filtered list of dictionary entries (`src/dzll_launcher/mod_suggestions.py:80-92`, `231-238`). It cleans names again, groups mods by Workshop ID or compacted name, maintains per-server deduplication and name frequencies, constructs display/search entries, sorts them, and builds prefix/exact lookup maps (`src/dzll_launcher/mod_suggestions.py:57-63`, `110-149`, `203-228`, `231-288`). This is one global index over retained servers, not a redundant copy of the per-server search index.
6. The global suggestion index is replaced on every full load (including a provisional cached load followed by a successful fetch), and can be rebuilt again on a later suggestion request if it is empty while rows exist (`src/dzll_launcher/window.py:5395-5445`, `5795-5801`, `5934-5938`, `8655-8659`). Because `_ModSuggestionIndex.__len__` returns the number of mods, an empty-mod dataset can satisfy this retry condition repeatedly; that is a source-confirmed repeated-work path during user interaction, not evidence that it occurred in the supplied startup run (`src/dzll_launcher/mod_suggestions.py:47-49`).

### JSON decode inventory

| Consumer | Decode | Purpose and timing |
|---|---|---|
| Preview | `window.py:519` | Each loaded row during GTK row construction; names/count/first-eight preview. |
| Per-server search index | `mod_search.py:109` | Each loaded row during GTK row construction; ID/name/token matching sets. |
| Global suggestion index | `mod_suggestions.py:85` | Each retained object during GTK global rebuild; aggregate counts, display names and lookup maps. |
| Required-mod popover | `column_view.py:1329-1352`, called at `1666` | On binding visible/recycled rows; current required-mod names and tooltip/popover state. It is a separate GTK render cost, **outside** the two measured startup indexing buckets. |
| Join/preparation | `workshop_mods.py:19-53`, called by `window.py:11794-11801` and `11924-11931` | On-demand authoritative ordered, deduplicated positive Workshop IDs/names for preparation. Do not replace this with a possibly stale search/suggestion index. |
| Mod-name resolver | `mod_name_resolver.py:37-69` | On-demand direct DB scan for name resolution, outside the startup row-loader path. |

For a successfully loaded server with nonempty valid JSON, three whole-payload decodes therefore occur before the initial list is ready. This is **confirmed duplicate parsing of input**, while the three outputs have distinct semantics. Whether the same JSON text is shared by many different servers, and how many rows have empty/invalid payloads, was not measured. The suggestion code also creates an intermediate list of raw-string references (`window.py:8409-8416`) and a list of parsed dictionary references per payload (`mod_suggestions.py:80-92`). These are avoidable allocations in principle; their cost and peak-memory contribution are unmeasured.

## Consumers and compatibility contracts

- **Row display:** `mod_count` drives the Column View mod text/button and `mods_preview` participates in stable row display/caching (`src/dzll_launcher/column_view.py:1755-1766`, `1813-1826`; `src/dzll_launcher/ui_row.py:315-340`). Preserve the DB `modCount` override, eight-name truncation, empty/invalid JSON behaviour, original order and duplicate names in preview (`src/dzll_launcher/window.py:507-543`, `5834-5845`). Companion persistence also copies raw JSON, count and preview, and can reconstruct a standalone object from those values (`src/dzll_launcher/window.py:3527-3577`, `3579-3645`).
- **Per-server mod search:** `_build_filter_state()` parses `mods:`/selected chips into a query, and `_combined_filter_func()` calls `server_matches_mod_query(obj.mod_search_index, ...)` for each candidate row in mod-query mode (`src/dzll_launcher/window.py:8110-8114`, `8138-8153`). Preserve the index keys `ids`, `names`, `normalized_names`, `compact_names`, `tokens`, their frozenset/alias behaviour, exact numeric ID matching, alias expansion and text/token matching (`src/dzll_launcher/mod_search.py:36-38`, `64-88`, `99-146`, `149-213`). A preview or global suggestion entry cannot substitute for this index.
- **Suggestions and chips:** `_refresh_mod_suggestions()` uses `suggest_mods()`; `_resolve_exact_mod_chip()` scans global entries and uses the suggestion fallback (`src/dzll_launcher/window.py:8220-8261`, `8655-8676`). Preserve ID-first/name-fallback identity, one-server `server_count` deduplication, per-name frequency, canonical/display-name selection, `raw_names`, aliases, tokenization, sort order, prefix/exact maps and candidate ranking/cache semantics (`src/dzll_launcher/mod_suggestions.py:47-67`, `95-149`, `172-228`, `231-288`, `431-529`). Rebuild must replace query cache and clear `_mod_suggestion_last_rows` (`src/dzll_launcher/window.py:8409-8417`).
- **Raw JSON authority and later parses:** `ServerObject.mods_json` is retained for the row popover, join/preparation and Companion snapshot (`src/dzll_launcher/ui_row.py:452-454`; `src/dzll_launcher/column_view.py:1658-1668`; `src/dzll_launcher/window.py:3565-3568`, `11794-11801`, `11924-11931`). Keep raw JSON available and preserve on-demand join parsing. The loader is the only active assignment of `mod_search_index`, and each DB reload constructs new objects/indexes; current live A2S updates do not rebuild these mod indexes (`src/dzll_launcher/window.py:5906-5909`, `7444-7469`). A new cache/sidecar must invalidate on every DB replacement, including cached/provisional and manual reload, and must not mix endpoint generations.

There are subtle nonidentical edge rules: preview treats `steamWorkshopId=0` as absent via `or ""`; search stringifies any non-`None` ID; suggestions also use `or ""` and skip entries with no cleaned name; join accepts positive integer IDs and deduplicates them (`src/dzll_launcher/window.py:523-532`; `src/dzll_launcher/mod_search.py:120-137`; `src/dzll_launcher/mod_suggestions.py:52-63`, `237-266`; `src/dzll_launcher/workshop_mods.py:37-53`). A shared parser can reuse the decoded list, but should not silently force one consumer's ID/name policy onto all others. Tests already cover name normalization and unusual ingestion cases (`tests/test_mod_name_normalization.py:209-239`; `tests/test_browser_server_ingestion_validation.py:470-512`).

## Why roughly 3.1 seconds is plausible, and what remains unproved

The source confirms three JSON decodes and repeated `clean_display_mod_name()` work for many mod items across 11,980 rows (`src/dzll_launcher/window.py:519-532`, `5834-5840`, `5906-5909`; `src/dzll_launcher/mod_search.py:109-137`; `src/dzll_launcher/mod_suggestions.py:85-92`, `237-266`). The global index additionally performs per-server sets/dicts, unique-mod entry construction, sorting and prefix-map creation (`src/dzll_launcher/mod_suggestions.py:231-288`). Both measured buckets run synchronously in the same GTK callback (`src/dzll_launcher/window.py:5788-5944`). These are confirmed architectural causes of substantial *possible* work and match the observed phase locations. They do **not** prove that JSON decoding, name cleaning, aggregation or prefix expansion individually dominate. The single run and opt-in per-row clocks may affect absolute durations. No claim of a 3.1-second recoverable saving is warranted.

## Safe candidates, ranked by benefit hypothesis and risk

1. **Measure one more narrow baseline before changing behaviour (low risk).** Repeat the 11,980-row run under the same input/settings several times. Add, in a later implementation task, only aggregate subphase timing (not server-level logging) for preview decode/cleaning, per-server search decode/normalization, and global decode/aggregation/finalization/prefix maps. Count valid/invalid/empty payloads, total mod items, unique mod identities and unique raw payloads; sample peak RSS. This can distinguish duplicate-decode benefit from global lookup-map cost.
2. **Share one decoded payload during a load, preserving independent outputs (moderate implementation risk, likely useful).** A private pure-Python helper could decode the accepted string once and pass the parsed list to preview and per-server search builders. The global builder could consume parsed/cleaned per-server contributions from the **final** `_obj_by_key` values rather than JSON-decoding the raw string again. Retain raw JSON on `ServerObject`, preserve each output's edge rules, and discard temporary parsed data after the global index is complete. This removes confirmed duplicate decoding and repeated cleaning opportunities; its actual time/RSS gain must be measured. Avoid constructing global counts directly from all DB rows because duplicate canonical endpoints are overwritten in `_obj_by_key` (`src/dzll_launcher/window.py:5912-5918`, `8409-8416`).
3. **Move only pure-data preparation to the DB worker if the remaining GTK cost warrants it (higher concurrency risk, potentially larger responsiveness gain).** JSON decode, name normalization, per-server search sets and global suggestion aggregation are pure Python; `ServerObject` property construction, `Gio.ListStore` mutation and GTK presentation are not (`src/dzll_launcher/mod_search.py:99-146`; `src/dzll_launcher/mod_suggestions.py:231-288`; `src/dzll_launcher/ui_row.py:437-487`; `src/dzll_launcher/window.py:5873-5918`). A worker result must be immutable/plain data, tied to a DB generation, guarded against provisional load/final load/manual reload/shutdown, and have failure/submit recovery. CPU time may persist under the GIL; the expected benefit is shorter uninterrupted GTK work, not necessarily shorter wall-clock startup. Do not copy the contributor's worker-side GObject construction (`devReports/PR16_IMPROVEMENTS_TRACKER.md:83-109`).
4. **Consider in-memory keyed reuse only after measuring repetition (conditional, memory/invalidation risk).** A bounded cache by exact raw JSON could help if many servers share identical payloads; a full persisted/precomputed index is currently hard to justify because raw DB data, normalization code, canonical names, filters and generations can change. Cached mutable parsed lists must not leak across rows or survive a replacement DB without an explicit key/version and memory budget. Lazy global construction could move the pause to the first suggestion interaction and complicate empty-index fallback, so it is not the first recommendation.

The first code experiment should target the shared decode/cleaning seam while leaving GObject/model handling and join authority unchanged. Keep the public builder APIs or compatibility wrappers where practical, and compare the experiment with the official instrumented baseline before accepting it.

Existing normalization/ingestion tests are starting points (`tests/test_mod_name_normalization.py:209-239`; `tests/test_browser_server_ingestion_validation.py:470-512`).
- Compare complete global entries, `server_count`, `name_counts` effects, canonical names, ordering and `suggest_mods()` output/ranking/cache behaviour for alias, shorthand, ID, multiword and duplicate-server cases (`src/dzll_launcher/mod_suggestions.py:110-149`, `231-288`, `431-529`; `src/dzll_launcher/window.py:8220-8261`, `8655-8676`). Include duplicate canonical endpoints and the empty-index retry route.
- Verify cached/provisional then final DB load, manual reload, failed fetch, empty DB, filter/chip changes, and shutdown/late worker completion if work moves off GTK. Preserve raw-JSON popover and join/preparation paths; the search index is not the join-time mod authority (`src/dzll_launcher/window.py:5395-5445`, `11794-11801`, `11924-11931`).
- Re-run the same controlled profile with and without the candidate; report median/range for the two mod buckets, DB GTK callback, main-loop stalls, overlay dismissal and peak RSS. Distinguish phase savings from end-to-end gains. No benchmarks or regression tests were run in this read-only audit.
