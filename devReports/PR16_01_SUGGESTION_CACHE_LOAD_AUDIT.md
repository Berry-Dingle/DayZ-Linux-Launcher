# PR16-01 — suggestion-cache load audit

Date: 2026-10-11  
Repository: `/home/gbrown/GithubRepos/DayZ-Linux-Launcher`  
Scope: read-only source and report inspection plus in-memory, offline analysis. No DZLL or Steam launch, network access, dependency installation, Git mutation, or source/test/instrumentation/tracker edit.

## Evidence and limits

The supplied 11,980-server measurements show a warm-cache GTK DB callback average of **3,198 ms**, following **3,576 ms** with shared decoding and **4,140 ms** originally. The supplied cache has **20,197 entries**, is about **19 MB**, and takes **710–808 ms** to load; cold build/save takes **1,700 ms**. Those are runtime observations supplied by the maintainer, not timings collected in this audit.

The measured cache file was **not present** at the expected `$XDG_CACHE_HOME` fallback path in this workspace, so its exact bytes and actual disk-read time could not be inspected. For structural and stage-cost evidence, a one-off Python process read the local SQLite server DB using a read-only, immutable SQLite URI and built an index **in memory** with the current builder. No cache file or instrumentation was created. That DB held **11,874 accepted/canonical rows** and yielded **20,091 entries**. It is close in scale but is **not the same 11,980-row input** as the supplied benchmark. The process printed only aggregate counts, sizes and timings, never server/mod contents. The stage measurements are proxy microbenchmarks and cannot apportion the supplied 710–808 ms exactly.

## Current load path and consumers

1. `suggestion_cache_path()` resolves `$XDG_CACHE_HOME/dzll/mod_suggestions_v1.json`, falling back to `~/.cache/dzll` (`src/dzll_launcher/mod_suggestion_cache.py:19-30`). The file format is version 1, with `created_at`, an `index` body and SHA-256 digest (`mod_suggestion_cache.py:128-146`). The body contains every mod entry, `count`, `prefix_map` and `exact_compact_map`; the mutable query-result cache is omitted.
2. During `_load_rows_into_store()`, the row loop constructs current previews and per-server search indexes before calling `_rebuild_mod_suggestion_index()` on GTK (`src/dzll_launcher/window.py:5813-5827`, `5860-5874`, `5933-5938`, `5963-5971`). A first-use disk hit calls `load_suggestion_cache()` synchronously on that same GTK callback. Subsequent DB reloads use the in-memory hit and avoid disk parsing (`window.py:8447-8470`). The existing `global_mod_suggestion_index` timing encloses the disk load but does not split its stages (`window.py:5963-5971`).
3. The loader stats the file, reads at most 64 MiB plus one byte, then `json.loads(raw)` materializes the **entire** JSON object (`mod_suggestion_cache.py:101-109`). It checks envelope fields, version and timestamp (`:110-119`). For integrity it serializes the already decoded `index` again with sorted keys and compact JSON, UTF-8 encodes that result, computes SHA-256, and compares the digest (`:97-98`, `:120-123`). The digest covers the reconstructed canonical JSON bytes, not the raw file bytes.
4. `_restore_index()` validates all entry fields and reconstructs a **new dict for every entry**, tuples for name/token fields, a new prefix dict and a new exact dict with tuple posting lists (`mod_suggestion_cache.py:40-94`). It does not re-clean names or rebuild tokens. During this step, parsed lists/dicts and restored tuples/dicts coexist until return. A valid expired index remains active; monthly replacement uses a separate worker and generation-checked publication (`window.py:8499-8569`).
5. `suggest_mods()` directly probes both lookup maps for normalized/compact query strings, query tokens and aliases; it falls back to scanning all entries for a multiword miss, ranks matches using `server_count`, name, Workshop ID and `raw_names`, and stores query results in its separate mutable cache (`src/dzll_launcher/mod_suggestions.py:438-536`). `_resolve_exact_mod_chip()` also uses the same catalogue and suggestion path (`window.py:8247-8282`). Any disk-format reduction must restore equivalent entry fields and map behavior before these consumers run.

## Format-size breakdown

The in-memory proxy serialized with the **same compact JSON options** as the current writer produced **19,690,628 bytes (18.78 MiB)**. The supplied 19 MB cache was not available for exact inspection. Values below therefore describe the 11,874-row proxy, not the maintainer's file.

| Stored component | Proxy bytes | Share | Structural evidence |
|---|---:|---:|---|
| `prefix_map` | 12,096,983 | 61.4% | 430,423 distinct prefix keys and 894,806 posting references; about 6.37 MB of encoded keys and 5.30 MB of encoded posting lists. |
| `mods` entries | 6,668,388 | 33.9% | 20,091 entries. Repeated JSON field labels account for about 2.81 MB and field values about 3.61 MB. |
| `exact_compact_map` | 925,069 | 4.7% | 40,010 keys and 40,413 posting references. |
| Count and envelope | 188 | <0.01% | Version, date, digest, outer labels and `count`. |

The prefix map is the dominant disk structure, by a large margin. `_build_lookup_maps()` adds up to 32 prefixes from every normalized name, compact name, token and Workshop ID, then stores sorted postings for each distinct key (`src/dzll_launcher/mod_suggestions.py:203-229`). In the proxy, **369,171 of 430,423 prefix keys** have only one posting. The exact map repeats compact names and IDs already represented partly in the prefix map; it is still needed for exact keys longer than the 32-character prefix cap and for current candidate behavior (`mod_suggestions.py:209-225`, `466-480`).

`_build_entry()` sets `name` and `display_name` to the same string and copies the first normalized/compact tuple element into scalar fields (`mod_suggestions.py:129-150`). All **20,091** proxy entries had `name == display_name`, `normalized_name == normalized_names[0]` (or empty), and `compact_name == compact_names[0]` (or empty). These are **confirmed redundant stored values** in the current builder, although the consumer-facing fields must be restored. The three duplicate scalar values alone occupied about **1.10 MB** before their JSON labels/syntax. Compact positional entries could also remove most of the 2.81 MB repeated entry-label cost. Name/token tuples and lookup prefixes repeat text for different purposes; eliminating those requires more extensive schema and lookup changes.

Removing both lookup maps from the proxy file would reduce it to about **6.67 MB**, but rebuilding both from entries took about **694 ms** in one offline run. That would exchange disk space for almost the whole observed warm-load time on GTK. A smaller file is therefore not automatically a faster usable catalogue.

## Time-cost evidence and bottleneck assessment

The following stages were timed on the in-memory proxy payload with `perf_counter_ns()`. No disk read or GTK scheduling was included.

| Stage | Proxy timing | Interpretation |
|---|---:|---|
| `json.loads` of the 19.69 MB document | 184–247 ms across sampled runs | Confirmed substantial decode/object-allocation cost. |
| `_index_bytes(decoded["index"])` for integrity | 279–296 ms | Confirmed duplicate JSON serialization plus UTF-8 encoding. `sort_keys=True` sorts a very large map. |
| SHA-256 over the resulting bytes | about 7 ms | The **hash algorithm itself is small**; calling the whole 286–303 ms step “SHA overhead” would misidentify the cause. |
| Current `_restore_index()` | 170–429 ms across uncontrolled samples; 287–313 ms in three GC-separated comparisons | Validates and copies entries/maps, creating about 470,000 new posting tuples plus dicts. Variance indicates allocation/GC sensitivity. |
| Equivalent in-place validation and tuple conversion prototype | 158–160 ms in the same three GC-separated comparisons | Produced an index deeply equal to the current result; potential **130–155 ms** reconstruction saving. This was a one-off script, not a source change or accepted benchmark. |

The measured proxy stages are consistent with a roughly 775 ms total cache load, but the real cache's file-read cost, allocation peaks, GC behavior and hardware conditions remain unknown. The read path allocates a bounded 19 MB byte buffer; actual I/O can vary with page cache and storage. `json.loads` then allocates the parsed graph, `_index_bytes` creates another large string/byte buffer, and `_restore_index` duplicates many containers. These are **confirmed operations**, while their exact contribution to the maintainer's 710–808 ms remains a hypothesis until phase timing on that file. The current `mod_suggestion_cache_load` diagnostic reports only one aggregate duration (`window.py:8455-8466`).

## Options ranked by benefit evidence and risk

1. **Convert the decoded index in place after validation; retain version 1 (lowest risk).** Validate the existing entry/map containers, convert only list fields/postings to tuples, and reuse the decoded dicts rather than allocating parallel entry and lookup dicts. The offline proxy showed a 130–155 ms reconstruction saving and identical complete index values. Keep every bound/type/index check and return only after full validation. On failure, discard the partially converted, still-private parsed object and use the existing cold rebuild. This changes neither disk format, query code, monthly refresh, nor startup scheduling. It should also reduce peak live containers, but RSS benefit is unmeasured. **This is the recommended first experiment.**
2. **Hash the stored payload bytes in a versioned single-file envelope (larger possible CPU benefit, moderate format risk).** The current canonical re-serialization costs roughly 280–296 ms in the proxy; SHA-256 costs about 7 ms. A version-2 header containing the format marker, timestamp/digest and an exact JSON payload could verify the raw payload bytes before one `json.loads`, retaining strict bounds, atomic writes and the same restored index. It needs explicit old-version migration behavior and corruption/future-version tests. It could remove most canonical-serialization CPU, but the effect on real warm startup and first-run conversion must be measured before adoption. Simply deleting the checksum would weaken corruption detection and is not recommended.
3. **Compress the existing logical payload (large space saving, uncertain startup-time gain).** Proxy zlib level 1 produced **4.18 MB** (about 79% smaller) with ~46 ms compression and ~13 ms decompression; level 6 produced **3.35 MB** with ~210 ms compression and ~13 ms decompression. `json.loads` on the expanded data still took about 211–217 ms in one comparison versus 184 ms for raw data; that difference is noisy, not a demonstrated regression. Compression helps I/O only if actual file-read time matters and does not remove current canonical re-serialization unless combined with option 2. It adds a binary format/version and cold-save CPU, so profile read time first.
4. **Store compact entries or selected maps (higher compatibility risk).** Positional entry arrays and omission/restoration of the three proven duplicate scalar fields can save entry bytes, but require schema migration and exact restoration of public entry dictionaries. Dropping `exact_compact_map` might save ~0.93 MB if rebuilt exactly; dropping `prefix_map` saves ~12.10 MB but the measured 694 ms map rebuild defeats the warm-start goal. Prefix encoding or posting compression could reduce bytes but needs candidate/ranking equivalence tests across aliases, IDs, long keys and multiword fallback. Do not alter map construction or lookup semantics solely to shrink disk usage.
5. **SQLite, lazy loading or an asynchronous cache load (highest lifecycle cost for this question).** SQLite could index prefix-to-entry relations and avoid loading all postings at once, but would replace simple in-memory lookups with per-query database work and introduce connection/thread/atomic-publication rules. Lazy loading on the first autocomplete request risks moving a 700+ ms pause to typing. A pure-data worker can safely parse/validate the cache, but loading after the DB callback may delay autocomplete; loading ahead of it requires result handoff across provisional/final DB loads, generation changes and shutdown. It could reduce the GTK stall without necessarily reducing total CPU or startup wall time. The existing monthly refresh worker already handles replacement, but first-load availability is a different contract. Avoid these designs until lighter changes and timing data show a remaining worthwhile cost.

## Acceptance measurements and regression gates

- On the actual 20,197-entry cache, collect aggregate `perf_counter_ns()` timings for **stat/read, JSON decode, canonical serialization, SHA, entry validation/conversion, prefix-map conversion, exact-map conversion and total load**, plus byte size, map-key/posting counts and peak RSS. Use one summary line under `DZLL_PERF_LOG=1`, not per-entry logging. Repeat at least three warm-cache launches under the same DB/settings/hardware; report median and range. The file was unavailable in this audit, so this is the smallest profiling gap.
- For the in-place experiment, compare the restored index **deeply** with version 1, including every entry field/type, entry order, prefix/exact maps, empty index and query-cache reset. Compare `suggest_mods()` results/ranking across exact Workshop IDs, canonical names, aliases/shorthands, prefixes, token matches, long compact keys, multiword fallback and repeated queries. The existing cache and ingestion tests (`tests/test_mod_suggestion_cache.py:19-84`, `tests/test_browser_server_ingestion_validation.py:218-361`) are a starting point; add differential tests against the unchanged loader using representative and adversarial caches.
- Exercise missing/corrupt/oversized/incompatible/future-version files, invalid posting indices and malformed entry fields, with safe cold rebuild and atomic save. Verify stale 30-day cache remains usable through full A2S sweep and worker replacement; verify reload generation and shutdown rejection. Measure cold build/save and monthly worker cost too, even if their semantics are unchanged.
- Compare `mod_suggestion_cache_load`, `global_mod_suggestion_index`, GTK DB callback, main-loop stall, overlay dismissal and RSS to the supplied warm-cache baselines. A load microbenchmark alone is insufficient to claim startup improvement. Preserve current per-server preview/search and raw join-time mod parsing (`window.py:5860-5874`, `5933-5938`, `5916`; `workshop_mods.py:19-53`).

## Recommended next step

Keep PR16-01 **IN PROGRESS**. First profile the actual file's aggregate load stages, then implement only the in-place restoration experiment if its measured reconstruction cost is material there. Require exact index/query equivalence and the controlled startup comparison before accepting it. Consider the versioned raw-payload digest only if the remaining canonical-serialization cost justifies a format migration. This audit created only this report; the tracker, code, tests, instrumentation, Git state and existing artifacts were left unchanged.
