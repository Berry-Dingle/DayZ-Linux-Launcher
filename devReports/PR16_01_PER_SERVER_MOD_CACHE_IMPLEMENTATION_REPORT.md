## Identity, format and exact behavior

The new cache lives at `$XDG_CACHE_HOME/dzll/server_mods_v1.json`, falling back to `~/.cache/dzll`; it is distinct from the global suggestion file (`server_mod_cache.py:17-35`). A record is selected by normalized `ip:gport`, produced by the existing endpoint validation and `fav_key()` (`window.py:495-496,5759-5782,5992-5998`; `server_endpoint.py:42-61`). Its digest is SHA-256 of the exact accepted raw `mods` string encoded as UTF-8, using `surrogatepass` for otherwise unencodable synthetic strings. `qport`, `modCount`, ping and other display fields are not cache identity. The body explicitly records `schema_version=1` and `normalization_version=1`; both must match. A byte-framed SHA-256 of the complete stored JSON payload detects damaged/truncated content before JSON decoding (`server_mod_cache.py:17-35,66-126`). Bump the normalization version when preview, name-cleaning or search-set semantics change.

Only derived preview count, preview string and four unique search sets are stored. On restoration the fifth `names` field is the **same frozenset object** as `compact_names`, preserving the current alias contract (`server_mod_cache.py:38-64`; `mod_search.py:142-149`). Record values, field types, list lengths, string lengths, file size (64 MiB) and endpoint count (50,000) are bounded; malformed/incompatible/oversized files are misses. The format uses JSON, never pickle. A correctly framed file with one malformed record causes that row to rebuild and repairs the final snapshot; unrelated valid records remain usable. Content checksum is accidental-corruption detection, not authentication against a writer that can deliberately recompute it.

The loader still assigns the accepted raw `mods_json` to each `ServerObject`. On a matching record, it restores preview count/string and frozenset index without calling `ParsedServerMods.from_json()` or `build_server_mod_index()` for that row (`window.py:5989-6020,6054-6085`). On a miss it follows the established `ParsedServerMods` -> `parse_mods_preview()` -> `build_server_mod_index()` path. The current DB's convertible `modCount` override is applied **after** either path (`window.py:6021-6025`); cache records never contain the override. Preview order, duplicates, eight-name truncation, the zero-ID edge rule, normalized/compact names, tokens and numeric IDs therefore follow the current builders. Duplicate canonical rows are processed independently in source order; the later row wins in the final endpoint map and persisted record, while existing source-store behavior is unchanged (`window.py:6088-6095`).

The existing global suggestion cache remains separate. A valid global cache uses no row parse on warm per-server hits. If the global cache is missing while some per-server rows hit, its current raw-JSON fallback builds the global catalogue from final endpoint objects, so it may decode those payloads **for suggestions only**. This avoids changing global suggestion aggregation and keeps per-server hit semantics exact (`window.py:6115-6125,8638-8650`). The row popover and both join/preparation entry points still parse raw `mods_json` independently (`column_view.py:1329-1352,1658-1669`; `window.py:12192-12200,12323-12330`). The cached search/preview result is never join authority.

## Load, write and failure lifecycle

The first DB application reads the disk cache once; later applications in the same window reuse its plain-data record map. Every accepted row recomputes its raw digest and compares the endpoint record. A provisional or failed-fetch load can use hits and populate an in-memory candidate, but cannot schedule a disk write. A successful final application with usable rows (including successful manual refresh) records the final endpoint set. A failed manual fetch does not apply rows. An invalid-only final row set does not prune the existing disk cache (`window.py:5749-5812,5922-5953`). Missing servers leave the live model immediately, then leave the disk snapshot only after successful final publication; a later reappearance rebuilds if its entry was pruned. In-memory records are reduced to the final endpoint set at scheduling time and capped after nonfinal loads.

Successful final application schedules a one-shot 25-second callback, keeping JSON serialization and fsync outside the startup GTK DB callback (`window.py:5803-5809`). The callback exits on shutdown, DB-generation mismatch, or an unchanged endpoint-to-digest map with no record repair. A needed write copies only plain Python records to the existing one-worker update executor. The worker sorts sets, validates records, serializes the bounded snapshot, writes/fsyncs a same-directory `.pending` file and returns its path; it creates no GObject and touches no GTK (`window.py:5855-5882`; `server_mod_cache.py:129-190`). The GTK completion callback checks shutdown/generation again before `os.replace`; stale stages are removed. A stage/submit/publish failure leaves live derived data and the previous cache file usable. A later DB load can retry. A timer-scheduling failure is swallowed because persistence is optional (`window.py:5883-5920`). Multiple queued generations may do wasted worker work, but only the current generation can publish.

The loader logs one `server_mod_cache_apply` phase only with `DZLL_PERF_LOG=1`: hits, misses, hit rate, current candidate count, file bytes, read, integrity, decode, top-level validation, digest matching, per-record restoration, miss rebuild, total cache-related time and process peak RSS. `server_mod_cache_write` reports result, generation, count, file bytes, worker serialization/write and total deferred duration on success (`window.py:5835-5853,5883-5920,6097-6112`). Existing `mod_preview_index`, `row_conversion`, `global_mod_suggestion_index` and GTK callback phases remain. The new work moves warm-hit lookup/hashing into `row_conversion`, so use the whole GTK callback and new cache phase together when comparing runs. No per-server logging or optional clocks are active when profiling is disabled. Peak RSS is process-wide high-water mark, not cache-attributable live memory.

## Runtime benchmark and rejection gate

1. Preserve the exact 11,980-server DB snapshot, settings, global v2 suggestion-cache file and machine conditions used for the reported 2,907 ms GTK callback / approximately 3-second stall. Keep the global cache warm and identical in all comparisons. Record its format, entry count and load phase to detect drift. Use an isolated copy of the per-server cache/profile data; do not overwrite the only known-good cache.
2. Collect at least three **cold per-server-cache** launches with no `server_mods_v1.json` and `DZLL_PERF_LOG=1`; record `server_mod_cache_apply` misses, DB callback, `mod_preview_index`, `global_mod_suggestion_index`, maximum main-loop stall, overlay dismissal and peak RSS. After each cold load, wait for the 25-second deferred `server_mod_cache_write result=published`, verify file size/entries and that no multi-second GTK stall coincides with publication.
3. Using that exact file and unchanged DB, collect at least three **warm** launches under comparable idle conditions. Expect near-100% accepted-row hits (duplicates included), no unnecessary rewrite, equal previews/counts/search results, and no new long GTK stall. Capture read/integrity/decode/record-restore/fingerprint/total cache times, whole DB callback, stall, overlay and RSS. Compare medians and ranges against cold and the supplied current baseline; do not subtract isolated proxy times from runtime measurements.
4. In a controlled detached DB copy, change a small known subset of raw `mods` strings (including names/order and IDs), change only `modCount` on another row, change only `qport` on another, remove/reintroduce an endpoint, and exercise provisional->final plus manual refresh. Verify exact hit/miss counts, affected row/search/chip behavior, final-only pruning and generation-checked publication. Separately test missing/corrupt/oversized files and failed write, and verify the global cache's monthly A2S-gated refresh and normal join preparation remain unaffected.

Accept persistence only if the warm median **whole GTK callback and maximum main-loop stall** both improve by at least 250 ms versus the comparable current implementation and by more than run-to-run variation, with correct cold/mixed/failure behavior, no deferred multi-second freeze and acceptable measured RSS. Treat the 250 ms as a predeclared practical threshold for this experiment, not a predicted result. Investigate or reject if warm hit restoration plus load approaches the 1,322 ms rebuild budget, if cold/cache-error paths materially lengthen startup, if deferred writes repeatedly fail or contend with live work, or if measured peak RSS/file growth is unacceptable (provisionally investigate >100 MiB extra peak RSS or a cache near the 64 MiB cap). If the gate fails, remove this experiment in a separate authorized change and evaluate plain-data worker preparation independently; no threading of GObject/model work was introduced here.
