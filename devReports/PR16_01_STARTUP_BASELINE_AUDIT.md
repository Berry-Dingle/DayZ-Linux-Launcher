# PR16-01 — Official DZLL startup baseline audit

Date: 2026-10-10  
Scope: read-only source and tracker investigation in the official repository. No application run, Steam launch, A2S query, timing experiment, dependency install, instrumentation, source edit, tracker edit, or Git mutation was performed. All references below are to the active `src/dzll_launcher/` tree unless stated otherwise. Timings and relative cost are **not established** by this audit.

## Executive finding

Database download and normal SQLite reading already run in a dedicated worker, and A2S requests run in a separate executor. The database completion callback still performs an unchunked, whole-database conversion to `ServerObject` instances, appends each to the source `Gio.ListStore`, builds a global mod-suggestion index, snapshots sort keys, scans and sorts the entire source model, and replaces the visible `Gio.ListStore` on the GTK thread. At about 12,000 rows these are confirmed *architectural main-thread workloads*, not confirmed measured startup bottlenecks. A cached-DB watchdog can additionally read SQLite synchronously on GTK. No source evidence establishes which operation causes the reported spinner pause or how long official startup takes.

## Main-thread work that can be expensive at 12,000 servers

- Before the list: window/widget/CSS construction and local persisted-state/Companion loading are synchronous in the window constructor (`window.py:675-784`, `862-917`, `1029-1041`, `1115-1161`, `1276-1309`). Their actual cost is unknown.
- In the DB callback: whole-list endpoint validation and map counting (`window.py:5662-5682`, `maps.py:50-70`), dropdown model replacement (`window.py:2282-2309`), and a possible second entire load following the watchdog (`window.py:5395-5404`, `5458-5465`).
- In `_load_rows_into_store`: per-row endpoint and display normalization, **two** mod JSON parses/index passes (`window.py:5757-5760`, `5823`; `mod_search.py:99-135`), `GObject` creation/property writes, individual source-store `append`s, then a separate global mod JSON aggregation/index pass (`window.py:5795-5831`, `8242-8250`; `mod_suggestions.py:231-268`). These loops scale with row/mod counts; no per-stage timings exist.
- Source-store sort snapshots loop over all items (`window.py:5958-5964`); visible-list rebuild scans/filter-tests every source item, sorts matched items and performs a complete model splice (`window.py:6016-6036`, `6047-6111`, `6120-6146`). The default `load` filter path rebuilds even when its state is unchanged (`window.py:8906-8910`). A successful warmup's automatic ping sort can rebuild again before reveal (`window.py:6477-6484`, `9435-9440`). GTK splice may trigger additional binding/layout work outside the measured Python call.
- Warmup orchestration itself sorts all keys into rank bands, allocates a queue and warmup set, pumps tasks and applies result batches on GTK (`window.py:5701-5709`, `6414-6459`, `6506-6545`, `6595-6605`, `7444-7469`). Query I/O is worker-side, but callback volume/property notifications can compete with rendering. The startup batch explicitly avoids a full live-result rebuild; the final ping sort still rebuilds (`window.py:7453`, `7811-7814`, `6477-6484`).
- The 30-second watchdog performs SQLite read and `dict` conversion on GTK (`window.py:5458-5465`, `db.py:123-157`). This is a confirmed main-thread I/O path and can be large; frequency and duration are unknown.

## Confirmed architecture versus unproven performance claims

**Confirmed from current source:** DB fetch and ordinary DB read are off GTK; watchdog cached read is on GTK (`window.py:5467-5487`, `5458-5465`). Row conversion, `ServerObject` construction, source append, global index, filter/sort and visible-store replacement are synchronous in GTK callback (`window.py:5662-5682`, `5718-5833`, `5966-6146`). Full display-store replacement occurs on load and again on normal successful warmup ping sort (`window.py:5832`, `6477-6484`, `9435-9440`). A2S network queries are submitted to a separate executor; results are applied on GTK (`window.py:6489-6605`). The reveal gate has a 65% completion threshold or 20-second timeout after queue setup (`config.py:105-111`, `window.py:6423-6455`).

**Suspected, not measured:** per-row Python conversions/mod indexing, property initialization, 12,000 individual source appends, full visible-store splice/GTK layout, Companion initialization, or result callback bursts might cause noticeable pauses. The tracker records an approximately 1-2 second pause during **PR testing**, but that is not an official-repository benchmark, causal attribution, or a verified improvement (`devReports/PR16_IMPROVEMENTS_TRACKER.md:90-114`). A 20-second reveal gate or DB/network delay may dominate wall-clock time even if row preparation is moved; this also requires measurement.

## Assessment of worker-side pure Python preparation

A worker could safely prepare immutable/plain-Python data from DB dictionaries: validate/normalize endpoints, coerce scalar fields, standardize maps, compute preview/search text and mod indexes, and possibly aggregate map/mod choices. These operations currently occupy the GTK thread (`window.py:5662-5682`, `5729-5793`, `5818-5823`, `8242-8249`) and are a plausible route to better responsiveness **if** profiling shows that they account for material main-loop time. It would not automatically reduce total CPU time; Python CPU work still competes under the GIL, adds handoff/copy/peak-memory cost, and leaves `ServerObject` creation/property writes, model population, filter/sort, splice, and GTK rendering on the main thread (`ui_row.py:437-487`, `window.py:5795-5828`, `5966-6146`). Moving `ServerObject` itself to a worker assumes safe GObject ownership/thread behavior that is not established here and is unnecessary for this hypothesis. The contributor approach and anecdotal pause should therefore not be adopted as evidence of benefit (`devReports/PR16_IMPROVEMENTS_TRACKER.md:83-114`).

## Lifecycle constraints for any later asynchronous design

- Carry one generation/token across DB fetch/read, prepared-data result, GTK apply, and A2S warmup. The current `_server_db_update_inflight` prevents a manual fetch during startup, while provisional watchdog data may still be replaced by a later success (`window.py:5384-5404`, `5458-5465`, `5493-5497`). Current `_startup_live_generation` guards A2S callbacks, not a future prepared-row callback (`window.py:5693-5695`, `6414-6417`, `6547-6559`).
- Define ownership for overlapping manual reload, filter/sort changes and Refresh All. A stale prepared data set must not clear or repopulate the source store after a newer operation; maintain current user sort/filter choice and live-result identity (`window.py:5493-5546`, `5719-5723`, `5830-5833`, `9367-9417`, `6842-7014`). Revalidate keys/rows at apply time and avoid applying stale A2S results to a replacement row generation.
- Worker failure and executor-submit failure need a GTK completion path that clears inflight/loading state and either uses existing valid rows/cache or presents a clear error. Current startup worker posts exceptions; submit failure completes presentation (`window.py:5406-5455`, `5467-5491`). A new preparation stage needs equivalent handling; partial model clearing before successful preparation would increase failure impact.
- Shutdown must invalidate pending prepared-row callbacks, cancel queued work where possible, and check a closed/generation flag before any GTK mutation. Current cleanup removes construction sources, invalidates live generation, and shuts executors without waiting (`window.py:2949-3003`, `3057-3060`, `3082-3112`, `3134-3140`). These are patterns to extend, not proof that an added callback would be safe. Preserve GTK/GObject construction and model mutation on the GTK thread.

## Minimal baseline profiling plan for a later authorized phase

1. Use a detached, representative ~12,000-row DB fixture and disposable HOME/XDG profile; preserve the real profile. Disable outbound DB/update/A2S activity through controlled fixtures or seams so repeated timing runs measure the same local data, then separately assess network/warmup timing if desired. Do **not** use packages or release trees as the source under test; use current `src/dzll_launcher` and record revision, row/mod counts, GTK/Python versions, settings, hardware and cache condition.
2. Make one small, opt-in monotonic timing trace covering: activation entry; window constructed/presented; startup idle submitted; update check/fetch/read start/end on DB worker; GTK completion entry; endpoint/map processing; pure row-data preparation; GObject creation; source-store insertion; global mod index; sort-key snapshot; filter scan, Python sort and display splice; first frame with nonempty list; warmup queued/threshold/timeout; final ping sort; overlay hidden; first responsive usable list; full A2S sweep end. Include thread ID, generation, row counts and outcome. Record the watchdog/cache path separately. This is a **proposal**, not instrumentation created in this audit.
3. Keep the existing main-loop stall diagnostic enabled for correlation, but collect delayed-tick timestamps/max/p95 and associate them with the phase trace. Measure process peak RSS externally; distinguish elapsed total activation-to-usable-list, activation-to-reveal, and activation-to-full-sweep. Run at least several warm/cold fixture repetitions with identical settings; compare distributions and the largest GTK phase/stall rather than one stopwatch value.
4. Use the measured phase split to choose a single next experiment: worker-side *plain data* preparation only if it occupies material GTK time; otherwise target the measured model/splice/render or pre-list operation. Benchmark the experiment against the untouched official baseline using the same fixture and verify reload, failed worker/submit, provisional watchdog, active refresh and shutdown races.

## Recommended next step

Keep PR16-01 **OPEN / ADAPT**. Authorize a separate, tightly scoped baseline profiling task using the plan above before selecting any implementation. In particular, measure `_load_rows_into_store()` by subphase and both initial and warmup-triggered visible-store rebuilds; those are the largest unmeasured main-thread paths by source structure. Do not transplant the PR's worker-side `ServerObject` construction or Refresh All coupling without independent timing and lifecycle evidence. Tracker requirements and closure criteria remain open (`devReports/PR16_IMPROVEMENTS_TRACKER.md:116-142`).
