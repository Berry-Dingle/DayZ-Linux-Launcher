# PR16-01 — GTK startup responsiveness design

Date: 2026-10-11  
Status: read-only architecture investigation; PR16-01 remains IN PROGRESS.  
Scope: current official checkout only. No DZLL or Steam launch, network operation, dependency installation, source/test/instrumentation/tracker/MEMORY.md/Forge edit, review-clone inspection, or Git mutation. Existing dirty and untracked files were preserved.

## Decision and evidence standard

**Recommendation:** First obtain a complete, same-run phase trace. If the row-construction/source-insertion loop accounts for a material share of the remaining pause, run a *startup-only, bounded GTK idle-batch experiment* that constructs `ServerObject`s and appends them on the main thread while keeping the displayed list unpublished until all rows are ready. Preserve the current synchronous loader for provisional replacement, manual database update, and legacy-model mode in the first experiment. Do not move GObjects into a worker. Do not ship batching merely because the 1.8-second pause is visible: retain it if the measured benefit is small or the lifecycle cost is disproportionate.

This is a recommendation for a later authorized experiment, not a claim that batching has already improved startup. A short time budget must be measured on the target GTK machine; an idle callback is not inherently small, and a single cache load, whole-list sort, or model splice can still block frames. If the phase trace instead locates the dominant cost in plain-data cache loading or in final model publication, use the alternatives below rather than batching the wrong operation.

Evidence classes in this report:

- **Maintainer-measured runtime, not rerun here:** on 11,980 servers, original GTK DB completion about 4,140 ms and largest observed main-loop stall about 4,222 ms; current warm-cache completion about 1,678 ms and stall about 1,837 ms. Per-server cache hit rate 99.77–100%; per-server cache processing about 310–320 ms; global suggestion processing about 360 ms. These are whole-run observations supplied in the task and recorded in `devReports/PR16_01_CACHE_VERIFICATION_REPORT.md`; no per-phase log from those same runs is available in this investigation. The earlier report records 2,727 passed and 24 skipped for the offline suite, not a test run made here.
- **Source-confirmed:** the code paths and ownership boundaries cited below from the active `src/dzll_launcher` tree. The older baseline/instrumentation/cache reports and tracker were reviewed, but their old line numbers and hypotheses were checked against current source.
- **Unverified:** the amount of the 1,678 ms attributable to scalar conversion, GObject work, source append, sort snapshot, visible rebuild, and deferred GTK rendering; whether the proposed batching improves animation on this machine; and the A2S 500/60 timing effect. No timing below is inferred by subtracting overlapping phases.

## Current startup control flow

1. First application activation constructs and presents `DZLLWindow` on GTK. The constructor creates `self.store` as the source `Gio.ListStore`, `column_view_store` as the active `Gtk.ColumnView` model through `Gtk.NoSelection`, six executors including single-worker DB and update executors, a browser-live timer, and a startup DB idle source (`app.py:80-110`; `window.py:815-820,1151-1174,1341-1346`). The optional legacy `Gtk.FilterListModel`/`Gtk.SortListModel` is separate and normally absent (`window.py:1153-1169`). Pre-window imports and construction are outside the DB callback.
2. The startup idle turns on the overlay and submits a DB worker. The worker checks updates, fetches/validates the DB, reads SQLite rows into plain dictionaries ordered by players and ping, then posts `finish_startup` with `GLib.idle_add` (`window.py:5434-5588`; `db.py:123-157`). The 30-second watchdog is exceptional: it reads the cached SQLite DB synchronously on GTK and may apply provisional rows; a later successful final result can rebuild the list (`window.py:5453-5476,5533-5544`). A failed fetch can use cached rows or complete with no rows (`window.py:5478-5531`). Startup submit failure completes presentation without applying rows (`window.py:5583-5588`).
3. On GTK, `_apply_db_rows()` validates every endpoint, prepares map choices and replaces the map dropdown model, then enters `_load_rows_into_store()` (`window.py:5759-5791`; map model `2322-2349`). The loader loads the bounded per-server cache once per window; clears the source store and endpoint map; normalizes each endpoint again; converts scalars/map/time; fingerprints raw mods, looks up or rebuilds preview/search data, applies the current DB `modCount` override; constructs each `ServerObject` with GObject property writes; attaches Python search/filter fields and `mod_search_index`; appends to the source store; and fills the endpoint/live maps (`window.py:5921-6114`; `ui_row.py:437-487`). Duplicate canonical endpoints remain separate source rows while the last object wins in `_obj_by_key` (`window.py:6088-6095`).
4. Still in the same GTK callback, `_rebuild_mod_suggestion_index()` accepts the already loaded global cache, loads/validates/restores it synchronously, or rebuilds it from final endpoint raw mod data and may save it synchronously on a miss (`window.py:6115-6125,8602-8664`; `mod_suggestion_cache.py:125-240`). Then the loader snapshots all GObject sort properties and calls `_on_filter_changed(reason="load")`. The active rebuild scans `self.store`, applies `_combined_filter_func`, sorts a Python list, and replaces all visible rows with one `column_view_store.splice`; the fallback removes/appends one by one (`window.py:6126-6138,6257-6264,6265-6587,9414-9495`). Model notifications, factory binding, layout, and drawing may continue after the Python callback returns. The `source_store_insertion` timer covers individual `append` calls, not the initial clear or delayed rendering.
5. After a usable nonempty final DB load, `_apply_db_rows()` marks Companion rows loaded, sets updating state, ranks endpoint keys in coarse `bm_rank` bands and starts the initial A2S sweep (`window.py:5791-5830`). Up to 32 query tasks are pumped through the startup live executor. Results return to GTK, are buffered and applied to existing objects. The initial visible list remains stable during background updates; startup result batches do not cause a structural rebuild (`window.py:6740-6797,6857-6956,7804-7829,8158-8173`). Completion of 65% of attempts among loaded rank-1000-or-better rows, or a 20-second timeout, flushes results, performs the automatic final ping sort/rebuild when the user has not changed sort, and dismisses the startup overlay (`window.py:6758-6762,6800-6838,10000-10005`; `config.py:105-111`). The rest of the A2S sweep continues after reveal. Overlay dismissal is only a proxy for a rendered, responsive first list (`startup_presentation.py:38-58`; `window.py:5411-5432`).

## Remaining cost: measured versus unmeasured

The current approximately 1,678 ms GTK callback and 1,837 ms delayed-tick observation establish a remaining visible pause, but they are different clocks and must not be arithmetically equated. The 250 ms diagnostic logs a tick interval after it runs; its figure includes the intended timer interval and potentially adjacent work (`window.py:1348-1368`). The measured 310–320 ms `server_mod_cache_apply` is **overlapping**: it combines cache load, per-row fingerprint, lookup/restore, and miss rebuild. Its row work overlaps `row_loop_total` and the residual `row_conversion`; it is not an extra phase to add to `row_loop_total` (`window.py:5835-5853,5938,5993-6019,6097-6114`). The approximately 360 ms global phase includes cache loading and surrounding index setup; `mod_suggestion_cache_load` provides its internal read/decode/integrity/restore split only when captured. Neither number proves a maximum frame pause by itself.

Existing instrumentation is sufficient to locate many synchronous subphases *if complete logs from the same run are retained* (`startup_perf.py:7-24`; `devReports/PR16_01_STARTUP_INSTRUMENTATION_REPORT.md`). Required additions for a later authorized benchmark are low-volume boundary markers for initial source clear, GObject post-constructor attachment/dict work, map Python versus GTK model replacement, `load` filter-state/legacy notification outside the rebuild, Companion/A2S queue setup, and callback exit. Record max/p95 delayed ticks or frame intervals, first nonempty rendered frame, first responsive interaction and whether the spinner animates while work is queued. The `startup_overlay_dismissal` marker alone cannot establish perceived usability. Log generation, provisional/final, cache state, rows and visible count; do not add per-row output. For cache internals use existing nested subphase fields before creating new timers. Measure RSS/USS separately; `ru_maxrss` is process high-water, not current ownership.

## Thread ownership and readiness boundary

**GTK main thread:** all `ServerObject` construction/property mutation, `Gio.ListStore` creation/append/splice, Gtk filter/sorter/model/dropdown changes, widgets, row bindings, overlay and presentation coordinator calls, live-result application, and publication of the browser's maps/index to UI consumers. The contributor's off-thread `ServerObject` construction has no verified GObject ownership safety; do not repeat it (`ui_row.py:437-487`; tracker PR16-01).

**Worker eligible as plain Python, with explicit immutable/snapshot inputs and no GTK/GObject access:** SQLite read already is; endpoint/scalar normalization, raw-mod fingerprint/parse/search-index derivation, per-server cache file validation/decode, global suggestion-cache file validation/decode/index restoration, map aggregation and other independent value preparation could be. Some current helpers read `self.settings`, favourites, last-played or mutable maps, so a worker version would first need bounded plain-data snapshots and exact freshness semantics. Python threads may still contend for the GIL and increase peak memory; eligibility is not proof of UX gain (`db.py:123-157`; `server_mod_cache.py:66-125`; `mod_suggestion_cache.py:125-240`).

**Bounded GTK idle work:** per-row normalization, cache lookup, `ServerObject` creation, property and index attachment, source append, and possibly a staged filter scan can be divided at row boundaries. A fixed row count alone is insufficient because misses and GObject notifications vary; check a monotonic deadline after a small minimum batch, then yield. Yielding only helps if no later single cache decode, sort or splice exceeds the frame budget. Python sort of all rows and a full visible splice cannot simply be made incremental without changing the ordering/publication scheme.

**Before browser use:** complete accepted rows and canonical endpoint map, current selected filters and correct favourite/played/mod-search fields, a correctly ordered visible model, row bindings capable of rendering, and a coherent A2S queue for that generation. Per-server preview/search data is needed for visible row behavior and selected chips. The cached global autocomplete catalogue can plausibly be loaded after initial publication, because filtering uses `obj.mod_search_index`, but this would temporarily leave autocomplete/exact-chip resolution empty or stale; it needs an explicit readiness contract and test. The full A2S sweep, persistent cache write, old-cache migration and monthly suggestion refresh are already deferrable. The present reveal gate still waits for warmup or timeout.

## Architecture comparison

| Approach | Responsive work it can remove or split | Safety and correctness cost | Verdict |
|---|---|---|---|
| **A. Small GTK idle batches** | Splits row conversion, GObject construction and source appends, giving GTK chances to draw spinner frames. No new worker or GObject ownership assumption. | Need a per-load transaction/generation, cancellation, error recovery, and atomic visible publication. Global cache decode, whole-list scan/sort/splice, and deferred render remain possible long pauses. More idle callbacks can increase total elapsed time. | Best *first architecture experiment* only if same-run row-loop/GObject/append measurements show meaningful headroom. Scope initially to empty-source normal startup, where display can remain empty until commit; keep other routes synchronous. |
| **B. Pure-data preparation in existing DB worker; GTK model construction remains** | Can move measured scalar/cache decode/validation work off GTK, including the approximately 360 ms global phase if its current cost holds. | Prepared results wait behind update check/fetch/read and may contend under GIL; handoff retains DB rows, cache documents and prepared rows at once. Requires cache error parity, settings snapshots, one ownership transfer, failure/submit recovery and stale-generation checks. GTK GObject/model costs remain unchunked. | Prefer if the same-run pure-data subphases dominate and model phases are small. Do not add another executor just for startup. |
| **C. Hybrid worker preparation plus incremental GTK population** | Addresses both pure-data and GTK per-row costs; strongest possible frame-smoothing route. | Two-stage generation protocol, more queued memory and cancellation states, worker failure paths, and unchanged final scan/sort/splice. GIL competition and later A2S overlap need measurement. | Consider only after a successful narrow A or B experiment and evidence of a second large phase. Never construct/mutate GObjects in worker. |
| **D. Smaller source-specific fixes / acceptance** | Preload a plain global cache in the DB worker; avoid a demonstrably redundant scan; or keep the current pause if no phase dominates enough. | Narrow fixes can help one workload but may add startup wall time, stale autocomplete, or new cache ownership rules; a no-change decision leaves a known 1.8-second pause. | Choose by same-run phase data. Do not alter sorting or warmup thresholds as an unmeasured proxy for GTK responsiveness. |

Batching `column_view_store` directly would expose an unsorted, partially filtered list and cause count/scroll flicker. The active displayed store should therefore receive one complete correctly filtered and sorted publication, while the overlay remains visible. Initial construction can use a private pending row list or staging source store; public `self.store`, `_obj_by_key`, live maps, map choices and suggestion state should be committed together on GTK only after success. This preserves favourites and Previously Joined filtering (`window.py:8247-8250,8270-8291`), selected mod chips (`8331-8357,8389-8397`), autocomplete (`8413-8454,9029-9065`), and the existing stable browser-live model behavior. The final one-shot source/model publication still needs its own measurement. A startup-only shortcut that appends into the live `self.store` while hidden must be guarded against filters, browser-live, Refresh All, Companion, legacy models, and provisional replacement reading a partial source; private staging is safer if those guards become extensive.

## Recommended first implementation experiment and safeguards

**Phase 0, measurement gate:** capture at least three comparable warm runs with the same 11,980-row DB, settings, caches and environment, including the existing child phases, callback timeline, stall/frame and first-render markers. Capture cold/invalid-cache cases too. If `row_loop_total` minus the cache-specific work, GObject constructor/attachments or `source_store_insertion` is not a material continuous segment, do not implement A. Treat the current approximately 1.8-second pause as an acceptable baseline. The experiment should target responsiveness, not a speculative total-startup reduction.

**Phase 1, narrow A experiment:** for normal first startup with no committed browser rows and active Column View, turn `_load_rows_into_store` into a resumable GTK-owned transaction only across the measured per-row phase. Set a provisional small deadline (for example, a few milliseconds, to be calibrated from frame measurements) and yield via a single tracked idle source. Keep overlay/spinner visible. Stage rows, endpoint/parsed/cache candidate maps and derived data without publishing them to consumers; preserve original order, duplicate-endpoint last-wins behavior, the current `modCount` override, raw `mods_json`, cache hit/miss semantics and cold fallback. At completion, run global suggestion policy, snapshot sort keys, rebuild from the full staged source, and publish the visible model once. Start A2S and the 25-second cache-write timer only after successful final publication; never start them against a partial generation. Preserve the synchronous path for manual DB update, provisional cached-DB then final replacement, failed fetch with cache, and optional legacy model until separately proven. If staging would require another full expensive 12,000-row source splice, measure that commit before proceeding; do not hide it behind a faster per-row trace.

**Transaction and lifecycle rules for any broader implementation:** assign a DB-apply token on submission and invalidate it on replacement, manual reload, shutdown or superseding application. Check token and `_shutdown_cleanup_done` before each idle slice and before publication; remove queued idle sources and release pending rows/caches on cancellation. Failed row conversion or GTK append must leave the previously published list usable and complete startup/error presentation rather than leaving an overlay indefinitely. Executor submit/future/GLib-post failures must have an explicit GTK recovery path; the current manual DB path has an unguarded submit (`window.py:5590-5643`), so a new stage must not inherit that gap. Do not call GTK from a worker. Guard the 30-second watchdog so it cannot apply provisional rows or synchronously read SQLite over an active final-stage build; retain the existing cached fallback semantics. On successful final replacement, invalidate earlier A2S generation and drop late results; current A2S callbacks already compare `_startup_live_generation`, but a new DB preparation token is still needed (`window.py:5811,6743-6744,6898-6909`). Manual Refresh All has a distinct generation, queue and final rebuild (`window.py:7184-7228,7247-7295,7328-7385`); hold it to the committed list or cancel it when replacing rows. Preserve user filter/sort changes made during a multi-idle build by taking their *current* state at publication; do not publish stale precomputed sort/filter order. Retain the current overlay coordinator ordering and do not report readiness before rows are published and a frame can render.

**Cache and memory ownership:** the per-server file is loaded once per window into `_server_mod_cache_records`, with a candidate map later copied for deferred publication (`window.py:5922-5937,5855-5876`). The global cache is a separate catalogue loaded only while `_suggestion_cache_ready` is false (`window.py:8602-8636`). A batch transaction must hold only the original DB rows, one bounded cache map, needed pending row objects/indexes and one candidate map; avoid a second full prepared dict per server. On cancel/commit clear parsed sidecars, old pending maps and idle closures promptly. A worker-preparation alternative should transfer plain data without retaining both old and new full snapshots longer than necessary. Existing memory evidence is inconclusive: the verification report's about 441-to-743 MiB high-water observations do not isolate steady-state cache use, and its isolated staging proxy saw a smaller transient rise. Measure time-aligned RSS/USS, high-water, cache sizes and row counts through apply, first frame, 25-second deferred stage and publication before accepting additional retained memory.

**Phase 2 only if Phase 1 succeeds but a long pause remains:** use its measured longest segment to decide whether to move bounded pure cache decode/scalar preparation into the existing DB worker (B), or to isolate/reshape the final filter/sort/visible splice. If the approximately 360 ms global load is the remaining longest block, a plain-data worker preload with a single guarded GTK index swap is narrower than a full hybrid. If final `splice`/render dominates, worker row prep will not fix animation; investigate GTK publication behavior and possibly a separate display-model strategy. Do not advance to C without evidence that both worker-eligible and GTK-owned portions materially contribute.

- Benchmark repeated controlled runs on the *same* detached 11,980-row database/caches and settings, with the current code as baseline and experiment under identical instrumentation. Record median/range and worst main-loop delay, p95 frame interval or missed frames, longest idle slice, spinner continuity, DB completion-to-first frame, activation-to-responsive-list, A2S threshold/reveal/full sweep, row/visible counts, current RSS/USS and peak memory. Run focused lifecycle/cache/filter tests, the maintained full offline suite and display-backed checks when implementation is authorized; none were run in this read-only task.

## Separate A2S warmup-target assessment — no change proposed here

Current warmup includes **all loaded rank-1000-or-better endpoints**, not a fixed 1,000 rows; it reveals after `ceil(0.65 × warmup_count)` *completed attempts* or the 20-second timeout, whichever happens first (`window.py:5818-5826,6758-6762,6791-6797,6901-6927`; `config.py:105-111`). A proposal to target the first 500 ranked servers at 60% would require about 300 completed attempts **if 500 eligible rows exist**; the exact threshold is conditional on the final chosen cohort. The queue currently orders all keys by coarse rank band, with stable within-band order inherited from `_obj_by_key`; it does not guarantee a true top-500 rank ordering (`window.py:5818-5819,6740-6746`; `db.py:147-151`). A 500-server policy therefore needs an explicit deterministic selection rule or it may exclude good candidates arbitrarily.

Source-based hypothesis: fewer required completions can shorten DB-ready-to-overlay-hide when the present 65% threshold, rather than the 20-second timeout, is the binding condition. It cannot shorten the GTK DB callback, remove its animation pause, accelerate DB fetch/read, or guarantee a quicker first rendered frame. If current warmup commonly times out, a smaller target might help, but the size of that effect is unmeasured. Conversely the earlier reveal uses fewer live observations: ping/order and online state may be less settled; favourites, Previously Joined, active filters and visible rows outside the first 500 may still carry DB values. The remaining A2S sweep continues and updates row properties, so users may see later status changes; current stable-list behavior avoids automatic membership splices but does not make unqueried statuses fresh. A smaller cohort also changes the moment of final ping sort/overlay dismissal, not the full sweep workload or global suggestion refresh gate, which waits for sweep completion (`window.py:6806-6838,6959-6984,8666-8700`).

Evaluate this independently with controlled A2S latency/failure distributions: record actual warmup count, completed/target attempts, threshold versus timeout reveals, DB callback end, first frame, overlay dismissal, first responsive interaction, visible rows' live-status coverage, and full-sweep completion. Compare 500/60 in a later separate experiment only if the current gate materially delays usability after GTK is responsive. Do not combine its benchmark with the main-thread experiment; no warmup threshold or scheduling was changed in this investigation.
